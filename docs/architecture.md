# Architecture

SupplyChainXAI is a production-oriented decision-support pipeline: every
number the system produces can explain itself, and every model that
produced a number is versioned, tracked and monitored.

```
DATA ──────────── raw CSVs (synthetic, seeded, documented)
 ↓
INGEST ─────────── schema coercion (supplychainxai/data/ingest.py)
 ↓
CLEAN ──────────── rule-based repair + audit report (data/clean.py)
 ↓
VALIDATE ───────── 15 integrity gates; CRITICAL aborts (data/validate.py)
 ↓
DATA QUALITY ───── continuous ERROR/WARNING sweep → data_quality_report.json
 ↓                 (monitoring/data_quality.py)
FEATURES ───────── leakage-safe lags / rolling / calendar (data/features.py)
 ↓
STORE ──────────── SQL warehouse: SQLite (default) or PostgreSQL via
 ↓                 DATABASE_URL (data/store.py) — one schema, one code path
WALK-FORWARD ───── rolling-origin expanding-window backtesting
 ↓                 (evaluation/backtesting.py), metrics per fold/SKU
EXPERIMENT ─────── every (SKU × model) run logged — params, fold metrics,
 ↓                 artifacts, tags (mlops/tracking.py → MLflow or JSON)
MODEL SELECTION ── composite of normalised WAPE/MAE/RMSE (config weights),
 ↓                 deterministic ties (evaluation/scoring.py)
MODEL REGISTRY ─── versioned models + promotion gates, incumbent archived
 ↓                 (mlops/registry.py, mlops/retraining.py)
FORECASTING ────── refit winner on full history → 30d forecast + 80% PI
 ↓                 (forecasting/models.py, forecasting/selector.py)
SHAP / PERM ────── why the model forecast this demand (explain/shap_bridge.py)
 ↓
RISK ENGINE ────── 6 alert families with evidence (risk/engine.py)
 ↓
OPTIMIZER ──────── BUY/EXPEDITE/HOLD + supplier choice (optimization/engine.py)
 ↓
EXPLAINABILITY ─── exact additive BUY decomposition (explain/engine.py)
 ↓
BUSINESS KPIs ──── observed / estimated / simulated (monitoring/business_kpis.py)
 ↓
MONITORING ─────── drift (PSI/KS), PI coverage, model health, retraining
 ↓                 decision (monitoring/*.py)
FASTAPI ────────── REST + dashboard (api/app.py)
 ↓
DASHBOARD ──────── 9 views incl. Model Ops (api/static/)
```

## 1. Data pipeline (phases 1–2)

- **ingest** (`supplychainxai/data/ingest.py`): schema-enforced loading —
  every column coerced to its expected dtype, dates parsed tolerantly.
- **clean** (`clean.py`): rule-based repair with a full audit trail
  (`cleaning_report.json`): duplicate removal, negative-quantity handling,
  SKU normalisation, PO date-swap correction, open-PO status derivation.
- **validate** (`validate.py`): 15 business gates (referential integrity,
  domain rules, unique keys, one-primary-supplier-per-SKU…). CRITICAL
  failures abort the pipeline; the report is persisted.
- **features** (`features.py`): leakage-safe supervised frame per SKU/day —
  lags (1/7/14/28), shifted rolling mean/std (7/28), calendar features,
  promo flag, price, and a stockout-censoring indicator.
- **store** (`store.py`): dim/fact schema (`data/processed/analytics.db` in
  SQLite mode) queried with real SQL by the copilot. Setting `DATABASE_URL`
  to a `postgresql://` URL switches the same build/query code to PostgreSQL
  (`julianday()` consumer SQL is translated automatically — see
  `store.to_pg_sql`). `scripts/init_store.py` populates the store from the
  committed CSVs without a training run (used by Docker).

## 2. Dataset provenance

The dataset is **synthetic**, generated by `scripts/generate_data.py` with a
fixed seed. `mlops/provenance.py` writes
`data/processed/metadata/dataset_manifest.json`: dataset name, content-hash
version, generation timestamp, source type (`synthetic_generated`), row
counts, date range, SKU/supplier counts, schema version, and an explicit
statement that the data is not real production data. The dataset version is
embedded in every experiment run, model version and monitoring report.

## 3. Walk-forward backtesting (evaluation/)

`WalkForwardBacktester` (evaluation/backtesting.py):

- expanding-window rolling origins; the tail of each series is tiled into
  `n_folds` consecutive test windows of `horizon` days (`stride` spaces
  origins for sliding schemes);
- temporal ordering is asserted per fold (`train_end < test_start`), a
  fresh model instance is fitted per fold, and short series that cannot
  honour `min_train_days` fail loudly;
- every fold's metrics (MAE, RMSE, MAPE, WAPE, bias) are stored per model
  and per SKU — artifacts/evaluation/walk_forward_results.csv;
- the summary reports mean, median and standard deviation across folds and
  flags *unstable* model/SKU combinations (WAPE coefficient of variation
  > 0.5) so a single lucky fold cannot hide volatility.

## 4. Model selection (evaluation/scoring.py, forecasting/selector.py)

Per SKU, candidates are scored with a configurable metric — `WAPE`, `MAE`,
`RMSE` or the default **composite**:

```
composite = 0.50·norm(WAPE) + 0.30·norm(MAE) + 0.20·norm(RMSE)
```

(min–max normalised across candidates within each SKU; weights configurable
via `SCX_EVAL__W_*`). Ties break alphabetically — selection is
deterministic. The selection record (`model_selection.json`) stores the
selected model, metric, score, competing scores, fold configuration,
training/validation windows, dataset version, feature version, git commit
and timestamp. The legacy single-hold-out comparison is retained for
parity checks but is no longer the basis of selection.

## 5. Experiment tracking (mlops/tracking.py)

`ExperimentTracker` is the only interface business code touches. MLflow is
used when installed (`MLFLOW_TRACKING_URI` picks the server / file store);
otherwise a JSON-lines backend under `artifacts/experiments/` records the
same runs. Tracked per (SKU × model) run: parameters (model, horizon,
folds, seed), fold metrics and aggregate metrics, tags (project, SKU, model
family, dataset version, environment) and artifacts (forecast CSVs).
Tracking failures degrade, never crash the pipeline.

## 6. Model registry & promotion (mlops/registry.py, mlops/retraining.py)

- every selected model is registered as a `ModelVersion`: model_id, family,
  SKU, version (dataset version), training timestamp, dataset/feature/code
  versions, metrics, selection reason, artifact path, status
  (`candidate | staging | production | archived`);
- promotion gates: validation passed, no data-quality ERRORs, artifacts
  generated, and **candidate WAPE ≤ production WAPE × (1 + tolerance)**
  (tolerance default 5%, `SCX_RETRAIN__WAPE_TOLERANCE`). Failed gates keep
  the candidate; passing gates archive the incumbent;
- the registry file (`artifacts/registry/model_registry.json`) is the
  source of truth; `sync_mlflow()` best-effort mirrors versions into the
  MLflow Model Registry when a registry-capable backend is configured;
- fitted estimators are persisted per SKU
  (`artifacts/models/`, joblib) so every forecast is traceable to the
  exact object that produced it.

## 7. Retraining policy (mlops/retraining.py)

`evaluate_retraining()` fires when any trigger trips: portfolio WAPE ≥ warn
threshold, degradation ≥ `wape_degrade_pct` versus the previous-folds
reference, drift status warning/critical, interval coverage below minimum,
stale data beyond `stale_data_days`, new-data volume trigger, or the
scheduled interval (`max_model_age_days`) reached. It returns
`{"retrain_required": bool, "reasons": [...]}` and never mutates state —
retraining executes via `python scripts/train.py`, and replacement of the
production model still has to pass the promotion gates above.

## 8. Monitoring (monitoring/)

- **data quality** (`data_quality.py`): superset of the validation gates —
  schema drift, missing values, duplicates, invalid dates, domain rules,
  referential orphans, categorical domains, extreme demand outliers,
  freshness. ERROR findings mean the pipeline should stop; WARNINGs are
  recorded. → `artifacts/data_quality_report.json`.
- **drift** (`drift.py`): PSI (5 quantile bins, ±inf outer edges) + KS test
  on demand-level features, comparing the last 90 days with the *previous*
  90 days (adjacent-window level shifts, not year-on-year trend). Statuses
  healthy / warning / critical per feature and per SKU.
- **prediction-interval coverage** (`coverage.py`): empirical coverage of
  the 80% PI on the final hold-out per SKU and portfolio-wide, with a
  documented recalibration hint (`sigma_scale_for_target`) that is never
  applied silently.
- **model health** (`model_health.py`): assembles status
  (`healthy|warning|critical`), current vs reference vs baseline WAPE,
  drift, coverage, data-quality status, the retraining decision and a plain
  recommendation. Interval miscalibration contributes at most a warning.
  → `artifacts/monitoring/model_health.json`.
- **business KPIs** (`business_kpis.py`): observed (transactions only),
  estimated (model-dependent) and simulated (cost-heuristic) metrics,
  each labelled — no invented savings.

## 9. Risk engine (phase 4 — unchanged)

Six alert families (`risk/engine.py`), each alert carrying its evidence:
stockout risk (P(demand over effective lead > position)), overstock,
demand spikes (Welch level shift), supplier lead drift, abnormal
procurement (price z-score), supplier reliability. Planning uses
drift-adjusted effective lead times.

## 10. Procurement optimizer (phase 5 — unchanged)

Periodic-review policy per SKU: gross requirement (forecast over lead +
review), safety stock (z·σ from PIs widened by lead-time variability), net
requirement, pack rounding, supplier choice by effective-cost score with
drift/reliability/unproven penalties, order-by date.

## 11. Explainability (phase 6 + SHAP)

Two surfaces that answer two different questions:

1. **Forecast explanations** — *why did the model forecast this demand?*
   Global SHAP feature attributions for tree winners (optional, falls back
   to permutation importance) plus local per-day SHAP drivers for the
   horizon's first input row (top positive / negative contributors in
   units of demand), alongside the counterfactual momentum read.
2. **Recommendation explanations** — *why did the system recommend buying
   this quantity?* The exact additive decomposition (forecast demand +
   safety stock − inventory position + rounding), unit-tested to reconcile
   with the shipped BUY number.

SHAP never modifies the business explanation; it only adds attribution
detail to the forecast surface.

## 12. Copilot (phase 7 — unchanged)

RAG-shaped retrieval over the analytics warehouse: question → intent →
SQL/artifact context pack → optional LLM re-wording (strict grounding
prompt) or deterministic narrator → answer + sources. Works without any
API key.

## 13. Service & dashboard (phase 8)

- **FastAPI** (`api/app.py`): loads committed artifacts at startup (< 2 s).
  `/health` (liveness) and `/ready` (store + artifacts + registry checks).
  MLOps endpoints: `/api/model-health`, `/api/data-quality`,
  `/api/business-kpis`, `/api/experiments`.
- **Dashboard** (`api/static/`): vanilla JS + vendored ECharts, 9 views —
  the original 8 plus **Model Ops** (model health, data health, the
  walk-forward experiment table, and business impact with
  observed/estimated/simulated badges). Responsive to 390 px.
- **What-If Simulator**: unchanged — re-plans the portfolio under demand /
  lead-time / inventory / service-level shifts.

## 14. Deployment modes

| Mode | What | How |
|---|---|---|
| Local dev | SQLite + JSON tracking, no services | `pip install -r requirements.txt && python scripts/train.py && uvicorn supplychainxai.api.app:app` |
| Production-like | PostgreSQL + API containers | `docker compose up --build` (postgres + api, healthchecked) |
| With MLflow | adds tracking server | `docker compose --profile mlflow up`, set `MLFLOW_TRACKING_URI=http://localhost:5000` |

Configuration is environment-driven (`SCX_*` variables, see
`.env.example` and `supplychainxai/config/settings.py`); secrets only ever
come from the environment.

## 15. CI/CD

GitHub Actions (`.github/workflows/ci.yml`): ruff lint + format check →
unit/integration tests (SQLite, no external services, no API keys) →
PostgreSQL job (store round-trip against a `postgres:16` service) →
end-to-end pipeline validation (dataset regeneration, training with a
reduced fold profile, artifact assertions, API boot + health/readiness +
model-health + business-KPIs smoke) → Docker build + container smoke test
→ dependency audit + secret scan.

## Deliberate limitations

- Synthetic data (documented generator) — swap `scripts/generate_data.py`
  for a real extract; the pipeline only needs the same six tables.
- Single-echelon inventory, no budget constraints yet.
- PIs are residual-Gaussian; coverage is monitored and honestly reported
  (currently under-covering — see results.md) rather than assumed.
- The MLflow Model Registry mirror is best-effort; the JSON registry is the
  source of truth.
